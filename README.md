# villa-walk

Совместная 3D-бродилка по вилле: Fastify + ws + SQLite (better-sqlite3), клиент на three.js r128 (лежит локально в `public/vendor/`).

- Просмотр: `https://villa.sunsetsamui.com/`
- Редактор: та же ссылка с `?k=<EDIT_KEY>` (ключ в `.env`, готовая ссылка — `/srv/villa-walk/EDIT_LINK.txt`)

## Запуск
    cp .env.example .env   # задать EDIT_KEY (32 случайных символа)
    docker compose up -d --build
Данные хранятся на хосте в `/srv/villa-walk/data` (`villa.db`, `uploads/`, `models/`).

## Локальная разработка
Нужен Node 20+ (проверено на 22). Данные отдельно от рабочих: `.env.local` (порт, `DATA_DIR=./data-dev`, свой `EDIT_KEY`) и `data-dev/` лежат в `.gitignore`.

    npm ci
    # .env.local: PORT=3000, HOST=127.0.0.1, DATA_DIR=./data-dev, EDIT_KEY=<32+ случайных символа>
    # модель дома для локальной базы: data-dev/models/villa.glb (иначе возьмётся seed/villa.glb)
    npm run dev          # node --watch: сервер перезапускается при изменении server/*.js, клиент (public/) отдаётся с диска

Адрес: `http://localhost:3000`, редактор — тот же адрес с `?k=<EDIT_KEY>`. `npm test` запускает e2e-тесты (Playwright, нужен chromium; каждый тест поднимает свой сервер во временной папке). Тест `tests/house.e2e.js` на Windows падает на шаге 5 (12 замен `villa.glb` подряд, пока браузер держит файл открытым: `rename` поверх открытого файла на Windows невозможен), на Linux проходит; к текстурам это не относится.

## Как обновить модель дома
Модель лежит в томе данных: `/srv/villa-walk/data/models/villa.glb` (в контейнере `/data/models/villa.glb`). При первом старте её копирует туда `seed/villa.glb`, если файла ещё нет. Пересборка образа и перезагрузка страницы у участников не нужны: все открытые вкладки получают сообщение `house.updated`, в фоне грузят новую модель и подменяют старую. Мебель, участники, инструмент и позиция в прогулке сохраняются, перекраски применяются заново. Показывается «Модель дома обновлена».

Перекраски, для которых в новой модели нет материала или детали с таким именем, из базы не удаляются и не применяются; список выводится в консоль браузера (`Перекраски без материала…`). Имена мешей и материалов — ключи раскрасок, поэтому при экспорте из Blender их лучше не менять.

### Через сайт (редактор)
1. Откройте ссылку редактора (`?k=<EDIT_KEY>`, готовая — в `/srv/villa-walk/EDIT_LINK.txt`).
2. В верхней панели нажмите **«Обновить модель дома»**, выберите `.glb` (до 200 МБ), подтвердите (файл больше 30 МБ — предупреждение в окне). Полоса показывает загрузку; при ошибке появится понятное сообщение.
3. Сервер проверяет заголовок (`glTF`, версия 2), пишет файл во временный файл рядом и атомарно подменяет `villa.glb`. Прежняя версия уходит в историю.

### Через SSH
    scp villa.glb root@<сервер>:/srv/villa-walk/data/models/villa-new.glb
    ssh root@<сервер> 'cd /root/villa-walk && docker compose exec villa-walk node scripts/house-reload.js villa-new.glb'
Скрипт проверяет файл, переносит текущий `villa.glb` в историю, ставит новый, увеличивает версию и рассылает `house.updated`. Файл `villa-new.glb` после этого удаляется.

Если файл уже положили сразу поверх `villa.glb` (`scp … /srv/villa-walk/data/models/villa.glb`), запустите без аргумента: `docker compose exec villa-walk node scripts/house-reload.js` — он проверит файл, увеличит версию и разошлёт обновление (старая версия в этом случае в историю не попадёт, она уже перезаписана).

### Как откатить
- На сайте: **«История версий»** → у нужной даты **«Вернуть»**. Текущая версия при этом сама уходит в историю, версия увеличивается, всем уходит `house.updated`.
- Вручную: файлы лежат в `/srv/villa-walk/data/models/history/villa-<YYYYMMDD-HHMMSS>.glb` (время UTC). Скопируйте нужный в `models/villa-new.glb` и выполните команду из раздела «Через SSH».
- Хранятся последние 10 версий истории, более старые удаляются (только файлы истории).

### Технические детали
- Версия (число и дата) — в SQLite, `docs(coll='house', id='meta')`; отдаётся в `GET /api/state` и `GET /api/house` (список истории — только с ключом редактора). Клиент грузит `/models/villa.glb?v=<версия>`; файл отдаётся с `Cache-Control: no-cache` и `ETag`.
- Тесты: `npm i && node tests/house.e2e.js`, `node tests/thumbs.e2e.js`, `node tests/tex.e2e.js` (Playwright, свой сервер во временной папке).

## Текстуры по фото
Человек фотографирует плитку, дерево, камень или ткань, загружает фото, задаёт реальный размер фрагмента в мм и «заливает» им стену, пол или мебель так же, как цветом.

**Как это устроено**
- У геометрии дома нет UV (это боксы из Blender), поэтому текстура накладывается по положению: UV = мировая позиция (м) / реальный размер фрагмента (м), на плоскости, к которой повёрнута поверхность (пол и потолок — XZ, стены — XY или ZY; мягкое смешивание только на наклонных поверхностях). Шов плитки лежит на кратных размеру метрах мира, масштаб реальный (`tests/tex.e2e.js` измеряет шаг плитки по скриншоту: 0,6 м).
- Базовая мебель — то же в собственных координатах предмета (положение и поворот, без масштаба), поэтому текстура не плывёт при перемещении. Загруженные модели с UV получают обычную `map` с repeat и rotation (размер считается по габаритам модели, это приближение).
- Тон (`tint`) умножается на текстуру, фактура (`finish`) работает как у цвета. Одинаковый вид (материал модели + текстура + размер + поворот + сдвиг + тон + фактура) — один материал на все меши; картинка в памяти одна на текстуру; освобождаются, когда их никто не носит. На телефоне грузится копия 1024, на компьютере 2048; анизотропия — максимум устройства (на телефоне не больше 4).
- Встроенные процедурные текстуры рисуются на canvas на клиенте (паркетная доска 3 тона, ёлочка, плитка 600×600 и 300×600 со швом, мозаика 50×50, бетон, короед, травертин, ротанг, рогожка, белый кирпич). Их ключи есть и в `server/textures.js` (`BUILTIN_TEX`): при добавлении новой менять в обоих местах (тест проверяет, что сервер принимает все ключи клиента).

**Данные** (только добавлены новые поля, старая база читается как есть)
- Коллекция `textures` в той же таблице `docs`: `{name, file, file1024, thumb, sizeMm:[w,h], seamless, by, at}`; файлы — `DATA_DIR/uploads/textures/<id>.webp`, `<id>.1024.webp`, `<id>.t.webp` (256, превью). Каталог создаётся при первой загрузке.
- В `paint`, `parts` и `items` необязательное поле `tex: {id | builtin, sizeMm?, rot (0/90/180/270), offMm:[x,y], tint}`. Без поля всё как раньше. Цвет документа при этом сохраняется: «Убрать текстуру» возвращает его, а обычная заливка цветом, наоборот, снимает текстуру.
- Кусок или стена с собственной записью (`parts`) заменяет вид материала целиком: запись без `tex` — это плоский цвет, даже если у материала («все такие») есть текстура.

**API** (изменяющие запросы только с `x-edit-key`, иначе 403)
- `POST /api/textures` — multipart: поля `name`, `w`, `h` (мм), `seamless` (`1`), `crop` (`x,y,w,h` в долях 0..1 повёрнутого по EXIF кадра), затем `file` (поля идут до файла). jpg/png/webp/heic до 15 МБ, проверка magic bytes; sharp: автоповорот по EXIF, обрезка, до 2048 и копия 1024, WebP, превью 256. HEIC сервер не раскодирует (в готовом libvips нет HEVC): окно загрузки сначала отправляет оригинал, а при `heic_unsupported`/`bad_image` — JPEG, перерисованный браузером (iPhone и Safari открывают HEIC сами).
- `PATCH /api/textures/:id` `{name?, sizeMm?}`; `DELETE /api/textures/:id` снимает текстуру со всех поверхностей и предметов (рассылаются `paint.set`/`part.set`/`item.set`) и удаляет файлы.
- Рассылка по WebSocket: `texture.added|updated|removed`. `GET /api/state` содержит `textures`: читать может любой, менять только редактор.

**Управление (редактор)**
- Панель поверхности или предмета: вкладки «Цвет | Текстура». На «Текстуре» — сетка карточек (встроенные и загруженные), поиск, размер фрагмента (можно задать свой для этой поверхности), поворот на 90°, сдвиг X/Y шагом 10 мм, тон и фактура (тот же пикер), «Убрать текстуру». «Что красим» — как для цвета: все такие / эта стена или предмет / только этот кусок (V).
- Инструмент **T**: клик накладывает текущую текстуру; `[` `]` или колесо (в прогулке) листают; Shift+колесо — масштаб ±10%; **R** — поворот на 90°; **V** — что красим; пипетка **C** берёт текстуру вместе с параметрами. **Ctrl+Z** отменяет наложение и смену параметров (серия быстрых «+10 мм» — один шаг).
- Левая панель, вкладка «Текстуры»: библиотека и «Новая текстура (по фото)». Кнопка «i» на карточке открывает окно с превью плиткой 3×3, переименованием, размером и удалением (подтверждение в окне, не `confirm()`). Зрители видят библиотеку и окно, но только для чтения.
- «Новая текстура»: файл или камера (`capture="environment"`), рамка обрезки (по умолчанию квадрат по центру; перетаскивание, колесо или ползунок меняют размер; пропорции рамки равны пропорциям ширины и высоты в мм), выравнивание перспективы по 4 углам, «Сделать бесшовной» (растушёвка шва или зеркальная склейка — последняя удваивает картинку, и размер в библиотеке тоже), предпросмотр плиткой 3×3, размер фрагмента в мм (замок пропорций), название. Снимайте прямо, при ровном свете, без бликов; измерьте рулеткой, сколько мм по ширине попало в рамку.

## Выкатка (текстуры)
На сервере нужна только пересборка образа:
- Новая зависимость `sharp` (в `package.json` и `package-lock.json`). Ставится из npm готовым бинарником (libvips внутри), системные пакеты не нужны, `Dockerfile` не менялся: `git pull && docker compose up -d --build`. Образ вырастет примерно на 30 МБ; нужен Node 20.9+ (в образе 20).
- Переменные окружения, миграции базы и новые тома не нужны. Таблица `docs` та же, новая коллекция `textures` и поле `tex` появляются сами; старые данные читаются без изменений. Файлы лежат в существующем томе `/srv/villa-walk/data/uploads/textures/` (создаются при первой загрузке от пользователя контейнера 1000:1000, как остальные загрузки).
- nginx: `client_max_body_size 32m` уже перекрывает 15 МБ, менять ничего не надо. CSP без изменений. Резервная копия (`deploy/backup.sh`) уже архивирует `uploads/` целиком, текстуры в неё попадают.
- Откат: вернуть прежний образ. Старый клиент покажет поверхность с `tex` обычным цветом (цвет документа сохранён); загруженные текстуры останутся на диске.

## Выкатка (модели до 200 МБ)
Код: `git pull && docker compose up -d --build`. Переменные окружения, миграции и тома не нужны.

**nginx на VPS** (`/etc/nginx/sites-available/villa-walk`, образец — `deploy/nginx-villa-walk.conf`), в `server { listen 443 ... }`:

    client_max_body_size 210m;      # было 32m
    client_body_timeout 600s;

и в `location / { ... }`:

    proxy_request_buffering off;    # тело идёт потоком в контейнер, а не копится в /var/lib/nginx
    proxy_send_timeout 600s;
    proxy_read_timeout 600s;        # было 120s

Затем `nginx -t && nginx -s reload`. `location /ws` не менялся. Без этого загрузка больше 32 МБ получит 413 от nginx, а медленная — обрыв по таймауту.

**Как это устроено**
- Лимит 200 МБ: `MAX_MODEL_BYTES` в `server/index.js` (модели и «Обновить модель дома»), проверки в `public/app.js`. Сервер принимает файл потоком во временный файл (`<id>.part`), проверяет заголовок glTF (версия 2, длина) и делает `rename`; файл не меняется и не держится в памяти.
- Загрузка: полоса прогресса с процентами и скоростью (XMLHttpRequest). Перед файлом больше 30 МБ — окно «Модель большая…» с «Загрузить» / «Отмена».
- Скачивание у участников: `fetch` + `ReadableStream`, при модели от 5 МБ внизу панель с процентами, пока модель не пришла — серый бокс по габаритам. `/uploads/*` отдаётся с `Cache-Control: public, max-age=31536000, immutable` (имя файла уникальное), второй раз модель берётся из кеша браузера.
- Превью большой модели рисуется как обычно (модель скачивается обратно с сервера); если браузеру не хватило памяти, карточка остаётся с заглушкой, страница не падает.

## Прокси и сертификат
`deploy/nginx-villa-walk.conf` (WebSocket, `client_max_body_size 210m`, таймауты 600 с), сертификат Let's Encrypt (webroot), продление — системный certbot.timer.

## Резервные копии
`deploy/backup.sh` по cron (`/etc/cron.d/villa-walk-backup`, 03:17) → `/srv/villa-walk/backups/`, хранится 14 дней.

## Протокол
`GET /api/state`; `GET /api/house`; `POST /api/house`, `POST /api/house/restore {name}`, `POST /api/house/reload` (multipart / JSON, заголовок `x-edit-key`); `POST /api/models` (multipart, заголовок `x-edit-key`); `DELETE /api/models/:id`; `POST /api/textures` (multipart), `PATCH|DELETE /api/textures/:id` (тоже с ключом редактора); WebSocket `/ws`:
`hello`, `presence`, `paint.set|reset`, `part.set|reset`, `item.set|delete`, `swatches.set` → сервер рассылает всем, включая отправителя; `model.added|updated|deleted`, `texture.added|updated|removed` и `house.updated {v, at}` рассылаются после загрузки/удаления/замены по HTTP.
